# Talking Points — Fab Yield & Capacity Decision Intelligence

## The 15-second pitch

"I built a decision-intelligence pipeline for semiconductor manufacturing on three real datasets: real fab sensor data to predict yield risk, real wafer defect-map images classified by a CNN I trained myself, and the published SMT2020 fab benchmark — all 10 of its real products — to model capacity, simulate the fab under different operating policies with a discrete-event twin, and optimize weekly production release with three Gurobi MILPs at three different scales. It's a real running app: FastAPI backend, a React frontend with its own dedicated methodology page, Docker image, CI running the test suite on every push, four live scenarios, and a live what-if panel you can drag yourself."

## The data (say this if anyone asks "is this real data?")

- **SECOM** (UCI ML Repository #179): 1567 real production lots from an actual semiconductor fab, 590 real anonymized process-sensor signals, real pass/fail outcomes, real timestamps. This is the standard academic dataset for fab yield/fault-detection research.
- **SMT2020**: the published semiconductor-fab simulation benchmark (Kopp, Hassoun, Kalir & Mönch, *IEEE Trans. Semiconductor Manufacturing*, 2020) — real reentrant process routes (500+ steps per product, revisiting the same tool groups dozens of times, just like a real fab), real tool counts, real MTBF/MTTR reliability data, real order-demand rates. It's the modern successor to the classic MIMAC benchmark family used in fab-scheduling research for decades.
- Be upfront if pressed: SMT2020 is a *published academic benchmark* representing realistic fab characteristics, not one specific company's proprietary data. I say that explicitly in the app's own README — I didn't fudge that line.
- **WM-811K** (Wu, Jang & Chen, *IEEE TSM*, 2015): 811,457 real wafer maps from 46,293 real production lots, 172,950 of them reviewed and labeled by real humans into 9 real classes. This is the standard academic dataset for wafer-map defect-pattern research — I trained a real CNN on it myself (see below), not a pretrained model I just plugged in.

## Key real results (numbers actually computed by the app — check current run, these can shift slightly by run)

- Yield model: ROC-AUC ≈ 0.71, PR-AUC ≈ 0.15 on a 6.6% real fail rate (imbalanced — that's why I used ROC/PR-AUC and 5-fold cross-validation with out-of-fold predictions, not raw accuracy).
- Capacity: **Diffusion is the real bottleneck** — only 10 furnaces, ~78% utilized at baseline release rate across all 10 real products, identified via Little's Law + Kingman G/G/m queueing theory applied to the real route data.
- Simulation: **CONWIP release control + Critical-Ratio dispatch beats uncontrolled FIFO push by up to ~29%** on mean cycle time depending on scenario, while capping peak WIP — a textbook factory-physics result (same throughput, less WIP, shorter cycle time), reproduced from a stochastic discrete-event simulation, not just cited from a book.
- Optimization: Gurobi's release-mix MILP, run across all 10 real products, shows this fab can only fill **~5% of real weekly order demand (19 of ~390 lots/week)** at the Diffusion bottleneck — and it finds that one product (part_5) is far more capacity-efficient than the rest, so the optimal plan loads up on it while still meeting every other product's minimum committed service floor. It also correctly flags when a scenario (a bigger diffusion outage, or a demand surge) makes even that minimum infeasible.
- Wafer defect CNN: **~74% macro-F1, ~94-95% accuracy** on a held-out real test set across all 9 classes — genuinely hard given the real class imbalance (147,431 "none" wafers vs 149 "Near-full" ones, roughly 1000:1). I report macro-F1 and per-class precision/recall instead of leading with accuracy, since a model that just predicts "none" every time would already score >85% accuracy on this data without learning anything.

## Why each technique, if they probe your reasoning

- **Random Forest + cross-validation** for yield: standard, defensible choice for high-dimensional (590 sensors), small-sample (1567 rows), imbalanced tabular data. I didn't reach for deep learning because the data doesn't justify it.
- **CNN for wafer defects, not a hand-engineered feature classifier**: this data actually justifies deep learning — 172,950 real spatial images, and defect patterns (Center, Donut, Scratch, etc.) are inherently spatial, exactly the shape prior a CNN encodes. Real wafer maps are variable resolution (346 distinct shapes in the labeled set alone), so I resize each to a fixed 64x64 with nearest-neighbor interpolation specifically to avoid inventing fake intermediate values between the real discrete die states (no die / pass / fail) that linear interpolation would produce. Trained with class-weighted loss, and the training split additionally caps the dominant "none" class (real: 117,944 of 138,357 training examples) to 25,000 so an epoch isn't almost entirely spent on the majority class — every other class keeps every real example, and validation/test stay the real, un-rebalanced distribution.
- **Little's Law / Kingman queueing**: closed-form textbook results (Little 1961, Kingman 1961), not fit to data — I unit-tested Kingman against the exact M/M/1 formula to make sure the approximation is implemented correctly.
- **SimPy discrete-event simulation**: because queueing theory alone can't capture reentrant flow, batch furnaces, or stochastic tool breakdowns (real MTBF/MTTR) — you need simulation for that, and I ran Monte Carlo replications, not a single seed.
- **Gurobi MILP**: because "which products to release this week under a capacity constraint" is a classic integer program (rough-cut capacity planning), and I already had a real Gurobi academic license on this machine.
- **Three solvers, deliberately different scale**: the single-week release mix is tiny on purpose (~10 variables) -- it's meant to be read in one glance. The multi-period plan is a real two-stage stochastic MILP: 10 products x 26 weeks of here-and-now release decisions, plus recourse variables for capacity shortfall under 10 Monte Carlo scenarios sampled from the benchmark's own real MTBF/MTTR (a compound-Poisson/Gamma sample-average-approximation of the renewal process). That's **3,380 variables and 5,990 constraints** -- past Gurobi's bundled 2000/2000 free-tier limit, so it actually needs the real academic license to solve. The third is the bottleneck dispatch scheduler: exact batch-formation (bin-packing, real BATCHMN/BATCHMX bounds) plus time-indexed parallel-machine sequencing at the real bottlenecks (Diffusion, Dry_Etch), minimizing weighted tardiness against real due dates -- **tens of thousands of variables** at realistic load. I built all three so I could point at the numbers and say "this one doesn't run without a real license; this one does" and mean it -- and explain *why* full-fab exact scheduling (every station, every lot) is combinatorially intractable (~180K variables even at modest scale) and the bottleneck-focused reformulation is the right engineering call, not a shortcut I didn't think through.

- **React frontend, server-rendered fallback for client routes**: the workspace and the methodology page are separate React Router routes so the methodology page has its own URL, not just a scroll anchor. FastAPI serves the built static bundle and falls back to `index.html` for any path that isn't `/api/*` or a static asset, so a direct link or a refresh on `/methodology` works — a common gap in hand-rolled SPA hosting that I tested for explicitly (`tests/test_api.py::test_client_side_route_falls_back_to_spa`), not just assumed.

## Likely questions and how to answer them

- **"What would you do differently with more time?"** — A real user-auth layer (OAuth/JWT) instead of the single shared API key I have now, the SMT2020 benchmark's second real fab archetype (HVLM) as a second selectable dataset, and a spatial-attention or ensemble model for the wafer CNN to push past the current classes it confuses most (visible directly in the app's own confusion matrix).
- **"Is this production-ready?"** — Closer than a typical portfolio project but still no. It has a Dockerfile, a docker-compose setup (app + Postgres), CI running the test suite on every push, structured logging and error handling in the API, a real persistence layer (SQLAlchemy + Alembic migrations, run history queryable via `/api/history`), optional API-key auth, and a DEPLOYMENT.md/SECURITY.md spelling out exactly what's still missing for real production use (rate limiting, TLS termination, real per-user auth instead of one shared key, multi-worker scaling). I'd rather list the gaps precisely than claim it's done.
- **"What's the hardest part?"** — Two answers, pick whichever fits the conversation. (1) Getting the real SMT2020 route data (500+ step, highly reentrant per-product routes) into a form that's both faithful to the raw benchmark and tractable for simulation/optimization — I aggregated ~100 individual tool sub-families into 12 station groups, and I can explain exactly why and how. (2) The WM-811K file itself wouldn't load at all with modern pandas — it was pickled under Python 2 with a ~2019 pandas version, and two separate compatibility breaks (a renamed internal module, and raw numpy bytes needing `latin1` decoding instead of the Python 3 default `ascii`) meant `pd.read_pickle` just threw `ModuleNotFoundError`. I wrote a small custom `pickle.Unpickler` subclass that redirects the old module path to its modern location and decodes correctly — a real, reusable fix, not a workaround that drops data (`pipeline/wafer_data.py`).
